# 天工系统更新、备份与回滚规则

状态：用户已确认的开发要求；2026-09-08归档，更新器未实现。适用四个产品独立或联合运行；天枢统一展示状态，各产品由自身更新组件执行。下述阈值为首版实施默认值，不是已经测得的最佳参数。

## 1. 发布与升级顺序

1. 自动检查和预下载，人工批准安装；仅升级变化的组件。先测试节点，再逐台灰度，不同时停掉所有业务节点。
2. 通常先升级能兼容旧App的天枢/天绘服务端，再更新天语/天行App，最后启用新能力。每个发行清单声明实际依赖顺序，不硬编码Web永远优先。
3. 无兼容路径时必须维护窗口：拒绝新任务、排空在途操作、保存会话草稿与检查点、备份后协调升级。任务结果未知时禁止自动重放外部动作。
4. Web更新的是服务与静态资源；浏览器提示新版刷新，保留未提交内容，不强制刷新。有活跃客服会话或RPA流程时暂缓更新，超时保持旧版并通知，不强杀业务。
5. 离线包走同样的签名、兼容、备份与恢复检查；独立App不强依赖天枢进程。未知或不兼容组件保持旧功能，禁止仅凭版本数字猜测兼容性。

## 2. 增量优先，全量兜底

- 每个目标版本必须有完整安装包；只有签名清单明确列出当前精确版本、平台、架构和基础文件树哈希时，才允许增量。
- 首版只接受“当前版本直接到目标版本”的一个增量包，不连打补丁。`maxDeltaGap=5`个本组件实际发行序号；跨度超过5、找不到直接包、基础哈希不匹配、目标强制全量、更新器太旧或补丁不适用，都走完整包。
- 版本号按整数百分位表示，项目0.09→0.10；增量跨度以本组件发行序号计算，不以字符串、浮点差值或别的组件迭代次数判断。
- 默认增量包达到完整包体积70%时直接全量。阈值必须由签名清单声明，可经测试调整；不由客户端随意扩大可用基础范围。
- 补丁只应用到同卷暂存的新版本目录，绝不原地覆盖正在运行的软件；验证重建后的完整目标文件树、包签名和哈希，成功后才进入安装切换阶段。
- 补丁下载中断可重试或续传，须绑定同一不可变资产、长度与ETag，最终重新校验。补丁合成失败丢弃的是本次暂存候选，不是旧版；可在原批准目标内退回全量。任何签名异常停止并报警，不以降级校验“兜底”。
- 全量包解决传输与文件替换问题，不会自动解决数据库或接口不兼容；缺少受测迁移/回滚路径时禁止升级，而不是盲装全量。

## 3. 断电、死机和更新器崩溃恢复

本地更新器使用单实例锁，持久化updateId、目标/基础版本、备份ID、当前阶段、旧版与候选路径、数据版本、失败次数。状态记录必须可校验、落盘并保留前一份；失败记录和日志不含秘密。

阶段顺序：下载→验证→排空任务/停止写入→一致性备份并验证→暂存合成→迁移/预检→切换→健康检查→提交成功→恢复接单。

程序目录、业务数据和更新事务记录分离。至少保留当前与上一个健康程序目录及完整原包。切换使用平台验证过的同卷替换机制配合持久化事务记录；不能把一次重命名或文件替换当成跨目录、数据库、多台电脑的原子事务。更新器独立于待替换主程序，不能覆盖自己后继续运行。

| 中断位置 | 下次启动动作 |
|---|---|
| 下载、验证、暂存 | 旧版不变；核对缓存后续传或重新下载 |
| 备份未完成/校验失败 | 禁止迁移与切换，保留原资产，回到旧版或维护状态 |
| 迁移或切换过程中 | 先读取恢复日志；禁止业务写入，根据数据兼容性恢复旧程序/升级前备份或继续受测迁移 |
| 切换后、成功提交前 | 候选版仅在维护状态健康检查；超时或连续失败回退，不接真实任务 |
| 成功提交后 | 按已提交版本恢复；若之后故障，按第5节处理新业务数据，不能盲目恢复旧备份 |

首版候选健康检查上限120秒、最多2次启动尝试；失败回退并隔离该候选，避免无限更新/回滚循环。健康检查包括进程、实际页面/API、数据库可读写测试、schema与接口匹配，测试写入在隔离数据或可回滚事务中。健康失败时不得仅因进程存活标成功。

断电恢复承诺是“状态可判定、可恢复、不混合半套程序”，不承诺硬盘物理损坏后仅靠同盘副本零损失。恢复日志损坏或资产状态不明时进入恢复界面并停写，不猜测成功。业务操作需另有幂等/回执查询，不以重装触发再次投放、上架或发消息。

## 4. 数据库与重要资产必须备份

- 覆盖数据库、任务与执行回执、客服未发送草稿、知识资料与附件、素材及用户上传文件、配置、身份/权限与配对凭据。先建立产品资产清单和一致性边界；程序包不含这些资产。
- 数据库使用其支持的一致性备份机制。SQLite优先在线Backup API；升级切换前仍需暂停所有相关写入并取得最终一致性检查点，不能只复制运行中的.db而忽略WAL。多进程共享库需统一停写；共享库只备份/迁移一次，统一锁定所有使用方。
- 备份ID关联数据库schema、程序/组件版本、时间、文件清单、长度、校验和及加密keyId。完成哈希和可读检查；数据库完整性检查通过，并在隔离副本执行打开/恢复验证。复制成功不等于备份可恢复。
- 空间预检必须覆盖下载包、解包/补丁临时峰值、新旧程序、完整资产备份、迁移临时空间及安全余量；不足则不开始切换，不靠自动删除最后可恢复备份腾空间。
- 首版建议至少保留最近3次成功升级前备份及30天内备份（满足两项保留要求的并集），每次额外保留最后一份已验证可恢复副本；清理另有审计，不随升级安装器删除。
- 企业正式升级前，重要资产还需有经验证的异盘或独立存储副本，避免同盘故障。备份加密、最小权限，密钥单独保护并验证可恢复；无可用密钥同样视为备份失败。任何必备资产备份失败均中止升级。
- 备份为本地/企业私有资产，不进入Git、GitHub Releases、遥测或公开日志。

## 5. 回滚规则

程序回滚与数据恢复必须分开判断。每版记录schema兼容范围、迁移前置条件、可退目标及受测恢复路径。安全更新清单回滚保护不得阻止本次事务回到已批准的已知健康版本；禁止任意远端旧清单触发降级。

1. 新旧程序可读写同一schema：切回已验证旧程序，保留当前业务数据。
2. 新schema不兼容旧版，且升级后尚未开放接单/产生新业务写入：停止全部写入，保留失败候选的数据副本，再从已验证升级前备份恢复一致资产集，切回旧程序并验证。
3. 升级后已有新业务写入：禁止自动用旧备份覆盖。立即停写并保全当前数据，采用已受测的无损回迁、兼容程序或前向修复；没有安全路径时进入人工恢复并明确不可自动回滚的原因。

任何版本若不能提供符合上述条件的回滚/恢复演练结果，不进入自动更新通道。破坏性schema变更必须维护窗口及人工批准；优先先扩展schema保持旧版兼容，旧字段清理放在回退窗口结束后的独立迭代。跨组件回滚遵循实际依赖，不能机械地逐个降版本。

## 6. 更新清单与发布门槛

清单至少声明product、platform、architecture、channel、componentVersion、releaseSequence、projectVersion、schemaVersion、兼容组件范围、最小更新器版本、升级依赖、完整包及直接增量包的不可变URL/长度/SHA、基础/目标树哈希、迁移和回退范围、资产备份要求、发布/失效时间、签名keyId和签名。

HTTPS加签名清单与包验证；客户端预置信任根，密钥轮换经旧信任链授权，拒绝过期、伪造、错误产品/平台、任意跳转域、路径穿越和越界解包。清单序号与本地高水位防止回放旧更新；人工离线恢复需独立授权记录。SHA校验本身不是来源认证。

顺序：构建完整包→从受支持基础版本生成补丁→验证补丁重建一致→安全与恢复演练→不可变附件上传→从发布源复核长度/哈希→签名清单→测试通道→人工批准生产通道。包上传失败不更新可激活清单；暂停有缺陷版本通过新的已签名清单撤回，不覆盖旧资产。更新规则与业务数据严格分开。

验收必须覆盖：下载中断、错基础补丁、坏签名/哈希、磁盘满、文件占用、任务忙、备份失败、每个持久化阶段断电/杀进程、迁移失败、健康检查失败、旧App/新服务混用、已产生新数据后的回滚拒绝、断网及离线恢复。分别验收Web服务和Windows App，模拟断电不代替目标部署环境恢复测试。

## 7. 技术依据与限制

- [SQLite Online Backup API](https://www.sqlite.org/backup.html)：使用数据库备份机制获取一致副本。
- [SQLite WAL](https://www.sqlite.org/wal.html)：WAL属于运行中数据库状态，不能只搬主文件冒充完整备份。
- [Microsoft File.Replace](https://learn.microsoft.com/en-us/dotnet/api/system.io.file.replace)：平台文件替换及备份原语可作实现候选，不代表多资产事务已实现。

本规则没有启用自动安装，也未提供签名密钥、可用补丁、schema迁移代码或数据库备份工具。实现与故障注入通过前，继续人工受控安装并保留原资产。
